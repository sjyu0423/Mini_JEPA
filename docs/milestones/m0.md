# Milestone 0: Simulation and dataset foundation

## Scope

M0 implements deterministic 2D ball motion, grayscale rendering, trajectory-level dataset
splitting, a framework-neutral sliding-window interface, visualization exports, and automated
tests. It does not include PyTorch, encoders, JEPA components, optimization, or evaluation of a
learned model.

## Design decisions

### Physics

The simulator uses a unit rectangular arena and treats a ball's center as constrained by its
radius. Motion is continuous and constant between impacts. Each timestep is resolved as a series
of time-to-impact events, so a fast ball may bounce multiple times in one frame without tunneling.
Simultaneous x/y impacts reflect both velocity components. Calculations use `float64`; stored
positions and velocities use `float32` to reduce dataset size.

A local NumPy generator is created from each trajectory seed. Dataset trajectory seeds are the
dataset seed plus a split-specific, non-overlapping trajectory ID. The same configuration and
seed therefore reproduce the same arrays without relying on global random state.

### Rendering

Rendering consumes positions after simulation and never changes physical state. Pillow draws a
white disk on a black 64×64 `L` image, exposed as a NumPy `uint8` array. Physics remains in
continuous arena coordinates and is independent of image resolution.

### Dataset and leakage prevention

Each compressed NPZ contains complete trajectories; no trajectory is divided between splits.
Split ID ranges are disjoint (`0+` for train, `1,000,000+` for validation, and `2,000,000+` for
test). `TrajectoryDataset` constructs window indices without duplicating image data. Its sample
surface contains rendered observations and target images—not privileged physical state.

Collision metadata records the count of x and y wall impacts during each frame transition. This
supports high-speed cases where a boolean flag would lose information. The montage outlines any
frame with at least one collision.

## Commands

```bash
uv sync
uv run ruff check .
uv run pytest
uv run mini-jepa generate --output data/m0 --train 16 --validation 4 --test 4
uv run mini-jepa inspect data/m0/train.npz --trajectory 0 --output artifacts/m0
```

## Acceptance results

Acceptance was verified locally on Apple Silicon with Python 3.12 through `uv`:

- dependency synchronization: verified
- deterministic trajectories and datasets: covered by tests
- elastic, in-bounds, corner, and multi-impact motion: covered by tests
- trajectory-level split separation: covered by tests
- four-frame inputs and configurable future target: covered by tests
- 64×64 `uint8` output: covered by tests
- sample PNG montage and GIF: generated through the CLI

See the final task report for the exact test count and generated paths from the acceptance run.

## Limitations

- The arena is axis-aligned and contains one ball with no gravity, acceleration, spin, or drag.
- Rendering uses hard pixel edges and does not model lighting, textures, or observation noise.
- Compressed NPZ files must be decompressed by NumPy when accessed; this is suitable for the small
  M0 corpus but may need sharding for large datasets.
- Physical metadata is stored beside images for evaluation and debugging. Downstream training code
  must continue using the model-facing interface to prevent privileged-state leakage.
- Collision counts use `uint16`; extraordinarily large velocities producing more than 65,535
  impacts in one timestep are outside the supported operating range.

## Readiness for M1

The stable array shapes, explicit split files, deterministic generation, and NumPy sample API are
ready for a future PyTorch adapter and encoder. M1 should consume only image observations and
targets during training, leaving positions, velocities, and collisions for analysis and metrics.
