# M5 — Final research release

## Objective

M5 converts the completed M0–M4 working repository into an auditable v1 research release without
changing architectures, retraining models, or publishing the project. It consolidates the research
story, preserves the measured results, verifies the executable workflow, and identifies what still
requires a release-owner decision.

## Release architecture

- `src/mini_jepa/physics.py`, `rendering.py`, and `dataset.py`: deterministic data foundation.
- `model.py`, `training.py`, and `torch_dataset.py`: historical M1 JEPA training path.
- `evaluation*.py`, `probes.py`, `baselines.py`, and `metrics.py`: frozen-representation analysis.
- `m3_*.py`: controlled temporal/objective/horizon experiments and diagnostics.
- `demo.py`, `demo_server.py`, and `demo_assets/`: real-checkpoint local prediction interface.
- `tests/`: unit, integration, leakage, alignment, checkpoint, and release-document checks.

## Release changes

- Replaced the milestone-oriented README with a project-level overview, measured results,

- Added a research overview, portfolio summary, and artifact provenance/checksum record.

## Verification protocol

The final audit covers:

1. `uv sync --locked` from the checked-in lockfile.
2. Fresh seeded sample generation and montage/GIF inspection output under `artifacts/m5/`.
3. Historical M1 and selected M3 checkpoint/probe loading and finite inference.
4. CLI discovery for generation, training, evaluation, experiments, and demo entry points.
5. Loopback demo startup and API health response.
6. Full pytest, Ruff lint, Ruff formatting, source/wheel build, and packaged demo-asset inspection.
7. SHA-256 comparison of locally available research artifacts against recorded provenance.
8. Scans for broken local documentation links, private workstation paths, credential-like strings,
   and unexpectedly tracked large or generated files.

Measured command results are recorded in the final M5 handoff rather than fabricated in advance.

## Research conclusion

Mini-JEPA learned a representation that supports much better future-position decoding than a random
encoder. The best GRU run improves M1 test and OOD error, and the multi-seed GRU family shows a clear
OOD benefit. The family mean does not beat the historical M1 in-distribution result, so the evidence
supports improved robustness under the tested speed shift rather than a universal architecture win.
Collision-heavy motion remains the principal failure mode.

## Known limitations

- Exact historical evaluation requires ignored local model and dataset artifacts.
- Neural training is seeded but not guaranteed bitwise reproducible across CPU/MPS and library builds.
- The synthetic single-ball domain is too narrow to justify claims of general physical understanding.
- The demo displays horizon-1 predictions, not a validated autoregressive rollout.
- Public release has not been tested on non-macOS platforms.

## Publication blockers and owner actions

The repository has no commit history yet, so there is no immutable source revision or release tag.
It also lacks a chosen software license, public checkpoint hosting, a model card, citation metadata,
and a clean-machine cross-platform verification record. The release owner should resolve those
items, create the initial reviewed commit, and only then tag and publish v1.0.0. M5 does not commit,
push, merge, change branches, retrain, or deploy.
